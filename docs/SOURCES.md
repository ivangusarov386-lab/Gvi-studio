# Источники и расчёты ГТО

Статус: реальные таблицы и их схема не предоставлены. Ни одна гипотеза ниже не утверждена как правило реальной системы. Перед реальным подключением требуется согласование. `GTO_RULES_CONFIRMED=true` — технический предохранитель, не замена согласованию.

## Канонический контракт адаптера

| Источник | Поля | Значение |
|---|---|---|
| Регистрации | id, participant | стабильный уникальный ID регистрации и отдельный ID участника |
| Регистрации | registeredAt | момент заполнения, ISO 8601 с Z или явным смещением |
| Регистрации | eventDate | календарная дата мероприятия YYYY-MM-DD |
| Результаты | id, participant | ID попытки и стабильный ID участника |
| Результаты | resultAt | дата/время попытки, ISO 8601 с Z или смещением |
| Результаты | status, level | статус сдачи и уровень из источника; сопоставление явными словарями |
| Оба | category (необязательно) | согласованный организационный признак, без персональных значений |

Точные заголовки задаются в серверном JSON, могут быть разными на двух листах. Дублирующийся/пропавший заголовок — ошибка источника. Идентификаторы никогда не передаются клиенту. Номера строк не являются стабильными ID. ФИО не использовать как уникальный ключ. Без подтверждённого ключа уникальности реальные метрики включать нельзя.

Текущий адаптер поддерживает только указанный строгий формат дат. Он **не угадывает** локальные строки DD.MM.YYYY, числа Google serial date, локальное время без смещения и многорядные шапки. Если реальная схема отличается, после её изучения потребуется отдельный преобразователь и тесты; не менять исходные формулы ради панели. Значения читаются как FORMATTED_VALUE. Диапазон должен включать шапку и иметь явную верхнюю границу (например A1:F10000). Если ответ заполнил всю ёмкость диапазона, чтение отклоняется, чтобы не публиковать потенциально обрезанные итоги. Адаптер не ищет структуру автоматически и не пишет в Sheets.

## Временные правила синтетического прототипа

1. Часовой пояс — Europe/Moscow. День регистрации/результата вычисляется из абсолютного времени в этом поясе. Дата мероприятия — отдельная календарная дата. Фильтры начала/конца включительны. Некорректные и перевёрнутые диапазоны отклоняются.
2. Одна регистрация — одна запись с уникальным `id`. Точные дубли по ID убираются. Если один ID содержит разные значения, все записи этого ID исключаются как конфликтные. Пустые ID регистрации/участника и некорректные даты исключаются и считаются отдельно.
3. Повторная регистрация одного участника с другим ID считается другой регистрацией. Число участников отдельно считается по уникальному `participant`. Правило «одна регистрация на участника и дату» пока **не принято**.
4. В результатах точные дубли ID попытки убираются; конфликтные ID и некорректные строки исключаются. Из оставшихся попыток выбирается последняя **внутри выбранного периода и категории**, а не лучший результат за всю жизнь. Более ранние попытки считаются отдельно. Совпадающие по времени, но противоречивые итоги одного участника становятся неизвестными.
5. `passed` означает только явный статус «сдал» после настроенного словаря. `not-passed` — только явный «не сдал». Всё остальное, включая пустое значение, считается неизвестным. Никаких расчётов знака по нормативам нет.
6. gold/silver/bronze учитываются только у последней попытки с явным `passed`. Пустой/неизвестный уровень — «уровень не определён», даже если «сдал». «Не сдал» одновременно с известным уровнем считается противоречием: неизвестный статус/уровень, отдельный счётчик.
7. Уровень из демо предварительный. Он не называется официально присвоенным знаком. Смысл реального столбца нужно подтвердить документально.
8. Счётчики исключённых строк и дублей относятся к целому загруженному источнику. Метрики результатов фильтруются по resultAt, регистрации — по registeredAt; дата мероприятия влияет только на регистрации. «Всего регистраций» учитывает выбранную категорию, но не период/дату мероприятия. «За период» учитывает период, «на дату» — период и выбранную дату. Без выбранной даты показаны все даты, что явно указано.
9. «Уровень не определён» включает явное «не сдал» без уровня, неизвестные статусы и «сдал» без уровня; это не число отказов/провалов. Каждый участник относится к одной категории распределения уровней.
10. Список категорий задаётся серверным `allowedCategories`. Неизвестные категории объединяются; значения строк не попадают в интерфейс произвольным текстом.

Правила проверяются в `tests/stats.test.js`; адаптер и HTTP-контракт — в `tests/server.test.js`. Изменение правил требует обновления тестов и версии контракта.

## Протокол и A2

Текущая панель не читает и не меняет «Протокол»/A2. Дата в интерфейсе фильтрует регистрации в памяти. Отображаемая проверка — сколько регистраций соответствует фильтру; она не доказывает правильность листа «Протокол». Фактическая проверка протокола помечена «не проверено». По настроенному ID есть ссылка на закрытую таблицу; доступ регулирует Google. Формирование протокола — отдельный согласованный этап.

## Что нужно от владельца для следующего этапа

1. Ссылки на таблицы регистрации и результатов, точные названия листов и строка заголовков. Отдельно указать, где «Протокол» и A2. Ссылки могут вести на приватные таблицы; публиковать их не нужно.
2. Только заголовки и 5–10 **синтетических** строк, показывающих даты, статусы, уровни, повторы и пустые значения. ФИО, УИН и реальные записи не присылать в чат/GitHub.
3. Какие поля надёжно определяют участника, регистрацию и попытку. Что делать с повторной регистрацией на одно мероприятие и повторной сдачей; последняя попытка, лучший результат или иной выбор.
4. Полный словарь статусов; точное определение «сдал»; где итоговый уровень и предварительный ли он либо официально присвоен. Часовой пояс и формат каждой даты.
5. Какие организационные категории разрешено агрегировать. Прототип поддерживает одну категорию; дополнительные независимые признаки добавляются после изучения схемы.
6. Существующая инфраструктура Google: есть ли Cloud-проект, сервисный аккаунт или уже защищённый Apps Script. На первом тесте — доступ читателя только к отдельным синтетическим листам. Секреты вводить через защищённые настройки среды, не в чат.
7. Где будет работать сервер панели, HTTPS-адрес/способ входа и кто имеет доступ. Подтвердить будущую синхронизацию через SQLite на этом сервере.

Только после успешного сравнения агрегатов с отдельной синтетической Google-таблицей — переход к реальным данным с минимальными правами.
